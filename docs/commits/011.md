## Resultado

Cinco rutas nuevas; la API pasa de 14 a 19 operaciones. Sin migración ni dependencias nuevas.

| Ruta                   | Acceso  | Comportamiento                                                                                   |
| ---------------------- | ------- | ------------------------------------------------------------------------------------------------ |
| `DELETE /products/:id` | Admin   | `204` si el producto no tiene movimientos; `409` si los tiene; `404` si no existe                |
| `GET /users/:id`       | Admin   | `200` usuario seguro; `404 "Usuario no encontrado."`                                             |
| `PATCH /users/:id`     | Admin   | Cambia `username` y/o `password`; `409` si el username está ocupado; `400` con body vacío        |
| `DELETE /users/:id`    | Admin   | `204`; `409` si es el último admin, el propio actor o tiene movimientos (en ese orden)           |
| `GET /health/ready`    | Público | `200 {"status":"ok"}` si `SELECT 1` responde en 2 s; `503` genérico si falla; siempre `no-store` |

- Cambiar una contraseña revoca las demás sesiones del usuario editado, conserva la sesión que hace la petición y reinicia `login_failures` y `blocked_until`.
- Al eliminar un usuario, sus sesiones caen por la FK `ON DELETE CASCADE` existente y su JWT recibe `401`.
- El borrado de productos usa el mismo bloqueo de fila que los movimientos y la edición de catálogo.
- `MovementsService` traduce a `401` la violación de la FK del responsable, para que eliminar un usuario mientras registra un movimiento no produzca `500`.
- Swagger documenta las cinco rutas; `ErrorStatus` admite `503`.

## SDD y documentación

La spec se escribió sin ver el código. Antes de implementar se contrastó con `src/` y se corrigió: rutas de archivos, `IdParamDto` (no existe; se usa `ParseUUIDPipe`), modos `'read'`/`'write'` de `adminTransaction`, FK de sesiones en CASCADE, throttler solo en `AuthController` y el número 011. De esa revisión salieron dos cambios de contrato aprobados por el usuario (D-60 y D-62):

- **Orden en `DELETE /users/:id`**: primero «último admin», después «auto-eliminación». Con el orden original la regla de último admin era inalcanzable, porque el actor siempre es admin.
- **Carrera usuario eliminado / movimiento**: nuevo criterio CA-18.

Código nuevo compartido: `src/common/database-errors.ts` (`isConstraintViolation` y los nombres de las FK de movimientos). En `UsersService` se extrajeron `USER_NOT_FOUND`, `isLastAdmin`, `lockUser` e `isDuplicateUsername`, que también usan `create` y `changeRole` sin cambiar su comportamiento.

Se actualizaron decisiones (D-59 a D-64), README, spec y tareas de 001 (contratos, RN-08 a RN-11, R-06 y F-06) y las notas de reemplazo en 006, 007 y 009.
